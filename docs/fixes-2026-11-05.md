### 2. Transactions
- **Fix:** Set up, Start, End, Cancel, Make a new code and the automatic end are each **one Firestore transaction**.
  - Each reads the exam state, checks it's still the exam this window acted on, then writes.
  - A window that loses the race writes nothing and shows "This exam was changed in another window. The screen now shows the latest."
  - Code: `src/app.js:694` (`examTx`), `:698` (new code), `:713` (set up), `:747` (start + freeze), `:767` (end), `:794` (cancel), `:674` (automatic end).
- **Questions and answer key saved in one batch** (`src/questions_upload.js:113`).

### 3. Server time
- **Fix:** `now()` = this device's clock + an offset measured against the hosting server's `Date` header (`src/app.js:2-20`).
  - Measured on load (max 3 s), every 10 minutes, and when the connection returns.
  - Used for the question timer, time left, the end check, the code age, and the start, end and code times the invigilator writes.
  - Test hook, localhost only: `?skew=<ms>`.

## Regressions found during Part 2 testing (all fixed)

| # | What broke | Cause | Fix | Retest |
|---|---|---|---|---|
| R1 | **Ended early → the test never closed and the attempt stayed `in_progress`** | Part 1's "wait for questions" guard checked the **current** exam's questions. After an early end the next exam is set up at once, so the guard returned before finishing. | The guard checks questions for the session's own exam (`src/app.js:412`) | attempt `submitted` with 3 answers, "Exam ended" ✅ |
| R2 | A late final save offered **Try again** and "Leave without saving" | the refusal is permanent | no Try again after a refusal; button reads Finish (`src/app.js:318`) | ✅ |
| R3 | The retention confirmation said "This removes **them**" for 1 result | wording | "it"/"them" by count | ✅ |
| R4 | The consent-time read after joining had no time limit | — | 15 s limit, like the other reads | — |

**Not app bugs:**
- **Test tool:** the Firebase emulator's browser-write channel wedged twice. All browser writes hung while REST writes and reads still worked. This started after I froze and resumed the emulator process for the slow-network test, and again after about 20 minutes with many tabs open. After a restart, writes were instant, and allowed → refused → allowed writes passed in 42 / 12 / 34 ms. So a refused write doesn't block later ones. Every write-dependent check was re-run on a clean emulator.
- **Hidden tabs:** Chrome slows tabs that have been hidden more than 5 minutes, which delayed some staff tabs' saves past the 30-second grace. On a phone in use the page is in front. A locked phone at the exact end would lose only the unsaved last answer; everything saved before is kept and marked ("Not submitted").

- The new page writes attempts as `results/<uid>_<track>_<examId>` with consent fields, which the old rules refuse.

   ```
   firebase deploy --only firestore:rules,hosting --project privantifyexam-be483
   ```
   *Or, if the GitHub Action publishes the page:* paste `firestore.rules` into Firebase console › Firestore › Rules › Publish **right after** the Action's hosting deploy finishes.

   - Open https://privantifyexam-be483.web.app/?admin, sign in, and check the dashboard loads.
